# 模块二：账号评分

输入一个藏宝阁账号地址，输出：

1. **指定式神的御魂搭配方案评分**（默认须佐之男 / 阿修罗）
2. **每种御魂在 6 个位置上的最快速**
3. **速度核心指标**（散件一速 / 招财一速 / 头速度 / 头尾数量，并与官方卖点交叉校验）
4. **副属性速度分布**（≥15/16/17、真17/伪17、满速、速度胚子、命中尾/抵抗尾）
5. **账号资产与式神概览**（六星/满技能、SSR/SP、图鉴收集、勾玉/金币/体力、皮肤、斗技…）

> 3–5 全部来自同一次详情请求，不额外增加藏宝阁请求。

> 这个模块**不需要登录藏宝阁**。用到的三个接口都是匿名的，
> 只是它们没有 CORS 头，所以必须由本机伴随服务代理（浏览器直连会被拦）。

---

## 一、怎么拿到可用的地址

### 关键限制：`ordersn` ≠ `eid`

商品页地址里长这样：

```
https://yys.cbg.163.com/cgi/mweb/equip/47/202610161701616-47-C8MSKXBXH4B4E
                                    ↑serverid  └────────── ordersn ──────────┘
```

但下面三个接口要的是 **`eid`**：

```
202610161701613-47-SMSV5P0UFDMEW
```

**两者无法互相推导**（实测结论，别再试）：

| 尝试 | 结果 |
|---|---|
| 详情接口传 ordersn（各种 Referer 都试过） | `物品不存在` |
| 商品页 HTML 里找 eid | 不含（HTML 只有 9 KB） |
| 两个 id 首段的差值规律 | **不稳定**：两组差 3、一组差 -99997 |
| 只传 `client_type` 靠 Referer 推断 | `请选择服务器` |
| 只传 `serverid` | `流水号不能为空` |

### 正确的取法：用「御魂搭配」弹窗的地址

1. 打开账号的商品详情页
2. 切到「**御魂**」标签，点「**御魂搭配方案**」
3. 弹窗出现后，复制地址栏里那条：

```
https://yys.cbg.163.com/cgi/mweb/yuhun-collocation?eid=<eid>&serverid=<id>&isH5=true
```

4. 粘进模块二的输入框

> 这条地址**直接带 eid**，一行就能解析，是最省事的输入方式。
> 也可以手动填 `eid` + `serverid`（serverid 就是商品页 URL 里 `/equip/<47>/` 那个数字）。

界面会识别两种输入：含 eid 的地址直接分析；只有 ordersn 的商品页地址则提示补 eid。

## 二、三个接口

| 用途 | 接口 |
|---|---|
| 方案清单 | `GET /cgi/api/get_yys_heroes_matching_plan?client_type=h5&eid=<eid>&obj_serverid=<sid>` |
| 单套评分 | `GET /cgi/api/compute_yys_heroes_plan?client_type=h5&eid=<eid>&obj_serverid=<sid>&heroId=<h>&planId=<p>` |
| 账号详情（取御魂仓库） | `GET /cgi/api/get_equip_detail?client_type=h5&serverid=<sid>&eid=<eid>` |

### 方案清单的返回结构

```json
{
  "status": 1,
  "data": {
    "389": {
      "name": "须佐之男",
      "plans": [
        { "id": "105", "desc": [
            { "label": "御魂套装",   "value": "海月火玉+荒骷髅" },
            { "label": "246号位选择", "value": "攻攻暴/爆伤" },
            { "label": "属性限制",   "value": "满暴" }
        ]}
      ]
    }
  }
}
```

`data` 的键是 **heroId**：须佐之男 = 389，阿修罗 = 364。

### 评分的返回结构

```json
{
  "status": 1,
  "msg": "该式神御魂搭配方式计算成功！",
  "data": { "result": {
    "suit_vals": {
      "damage": 26468.3,          ← 页面上显示的「总评分」
      "attackAdditionVal": 9874.5,
      "maxHpAdditionVal": 15043.6,
      "defenseAdditionVal": 630.4,
      "speedAdditionVal": 112,
      "critRateAdditionVal": 102,
      "critPowerAdditionVal": 268,
      "debuffEnhance": 14.5,
      "debuffResist": 11.3
    },
    "suit_data": [ { "slot": 1, "star": 6, "level": 15, "attrs": [...] } ]
  }}
}
```

**评分是服务端按该账号实际御魂算出来的**，不是静态攻略——同一式神不同套装得分不同
（实测须佐之男 5 套：27480 ~ 21278；阿修罗 11 套：28512 ~ 20591）。

## 三、速度怎么算

御魂的 `attrs` 里「速度」条目**已经是最终值**，不需要再换算。速度分两部分：

| 部分 | 数值 | 说明 |
|---|---|---|
| **副属性速度** | `attrs` 里所有「速度」之和 −（2 号位主属性 57） | 6★ 共 6 次 roll（初始 1 + 强化 5），每次上限 3，所以**单件满值 18** |
| **主属性速度** | 只有 2 号位有，满级固定 57 | 其他位置的主属性不是速度 |

```
总速度       = 副属性速度 +（2 号位主速度御魂 ? 57 : 0）
仅副属性速度 = 副属性速度
```

> ⚠️ **旧公式已废弃**：`attrs 速度 + Σ rattr.speedAdditionVal × 3`。
> `rattr` 里的 `speedAdditionVal` 是**每次随机 roll 的归一化比例**（0~1，×3 即数值），
> 全部加起来 ×3 恰好等于 `attrs` 里的副属性速度——两者是同一份数据，相加等于算两遍。
> 实测后果：非 2 号位出现 34.24 这种「单件速度」，而游戏里单件副属性速度不可能超过 18。
> 另外 `×3` 只对 6★ 校准过（实测 5★ 御魂 `attrs=6.00` 但 `Σrattr×3=3.00`），不能通用。

### 2 号位的口径（修正后）

2 号位的**主属性可以是速度**（满级固定 57），而且主速度御魂的 `attrs` 里会有**两条**「速度」：
`57.00`（主属性）+ `x`（副属性）。所以：

| 口径 | P2 显示 | 用途 |
|---|---|---|
| **总速度**（含主属性） | 57 + 副属性速度，最高约 75 | 这个位置最快能到多少 |
| **仅副属性速度** | 只算副属性，≤ 18 | 谁的副属性速度堆得好，**有区分度** |

界面上可以切换。修正后，**非 2 号位的单件速度全部 ≤ 18**；只有总速度口径的 P2 会超过 18。

> 旧实现用 `Object.fromEntries` 读取 `attrs`，重复的「速度」键只保留**最后一条**（副属性），
> 把主属性 57 弄丢了；`isMainSpeed` 也因此只认「没有副属性速度」的御魂
> （实测一个账号 159 件主速度御魂只认出 25 件）。现已改为按「2 号位出现 >18 的速度值」判定主属性。

### 回归校验

```bash
node tools/cbg/verify_speed_table.mjs --file "<缓存详情.json>" [--file ...]
```

缓存文件是 `get_equip_detail` 的响应（含 `equip.equip_desc`）。校验内容：
逐件御魂副属性速度 ≤ 18、非 2 号位单件总速度 ≤ 18、2 号位主速度御魂总速度 57~75、
6★ 副属性速度 == Σrattr×3、两种口径的速度表边界，以及服务端 / 两个 CLI 三张表一致。

## 四、速度核心 / 分布 / 账号概览 / 缓存 / 自动取分（A1–A3、A5、B1、B3）

A1–A3 都来自**同一次详情请求**，不会额外增加藏宝阁请求；A5 是本地结果缓存，B1/B3 是交互与诊断。

### 4.1 速度核心（A1，含官方交叉校验）

| 指标 | 口径 |
|---|---|
| **散件一速** | 6 个位置各自最快的总速度之和（含 2 号位主属性 57） |
| **招财一速** | 4 件招财猫 + 2 件任意套装（与官方 highlights 同口径） |
| **头速度** | 2 号位速度主属性御魂里，最高的副属性速度 |
| **头/尾数量** | 直接引用官方 highlights 的「N头M尾」；官方口径：头=2 号位速度主属性（副属性速度达标），尾=4 号位效果命中/抵抗主属性（副属性速度达标） |

详情接口的 `equip.highlights` 里通常已有官方标注的「散件一速 / 招财一速 / 头速度」。
服务端会把**本地复算值**和官方值逐项比对，页面显示「官方 xxx ✓」或「官方 xxx / 本地 yyy」。
实测两个样本账号的散件一速（157.92、154.45）与招财一速（152.60）完全一致；
不一致时会如实标出差异，不会藏起来。

> 这同时是一层回归保护：速度口径若再被改坏，页面会立刻出现「官方/本地不一致」。

### 4.2 速度分布（A2）

| 指标 | 定义 |
|---|---|
| 副属性 ≥15 / ≥16 / ≥17 | 副属性速度达到阈值的御魂件数 |
| **真 17** | 实际值 ≥ 17.00 |
| **伪 17** | 16.5 ~ 16.99（显示像 +17，实际不满） |
| 近满速 / 满速 | ≥17.5 / ≥17.99（6★ 副属性速度理论上限 18） |
| 速度胚子 | 未满级（<15）且带速度副属性的御魂 |
| 命中 / 抵抗 4 号位 | 四号位主属性效果命中 / 效果抵抗、且带速度副属性的御魂（数量 + 最高副属性速度）；官方「尾」还要求速度达标，所以通常比这里的数量少 |

### 4.3 账号概览（A3）

同一份 `equip_desc` 里还有大量列表接口不返回的字段，现在一次性展示：

- **式神**：式神条目数、六星数（含满技能六星数）、SSR / SP 拥有数（含重复）、图鉴收集率（`hero_history`）
- **资产**：勾玉、金币、体力、达摩、魂玉、皮肤券、皮肤总数、头像框总数
- **斗技/成就**：PVP 分数与排名、风姿度、荣誉分、勋章、成就数
- **御魂**：御魂总数、2 号位速度御魂数、首领御魂数

### 4.4 分析缓存（A5）

一次完整分析要 1 次详情（约 2.6MB）+ 1 次方案清单 + 每个方案最多 2 次算分，
反复点「重新分析」既慢又容易触发风控。现在结果按 `eid` 落盘缓存：

```
<仓库根>/cache/analysis/<eid>-<口径哈希>.json     # 已加入 .gitignore，不提交
```

> 文件名里的哈希由「式神组合 + subOnly 口径」决定，避免不同请求命中同一份结果。

- 默认 TTL **10 分钟**，可用 `--analysis-ttl <毫秒>` 或环境变量 `CBG_ANALYSIS_TTL_MS` 覆盖；
- 页面再次打开 / 刷新时优先命中缓存，接口返回里多出
  `cached`、`cachedAt`、`cacheAgeMs`、`cacheTtlMs` 四个字段；
- 页面顶部显示「结果来自 X 分钟前的缓存」；点「刷新」或「重新分析」时传 `refresh=1` 强制重新抓取；
- 缓存结构带 `version`，字段升级后旧缓存自动失效；写入失败不影响本次分析结果。

### 4.5 冷计算自动取分（B1）

站点对**从没算过**的账号，第一次请求只会返回「正在计算中！」。原来的做法是让用户自己过一会儿
点「重新分析」——但那会把详情、方案清单全部重拉一遍，既慢又多打请求。

现在新增 `POST /api/account/rescore`：

- 只重试上一次分析结果里 **pending（排队计算）的方案**，不重新拉详情、不重新拉方案清单；
- 从分析缓存里读上次结果（允许已过 TTL），把新分数合并回缓存；
- 单轮最多 `--rescore-max`（默认 20）个请求，请求间 sleep 700ms；一旦触发风控立即停止；
- 页面上的「自动取分」按钮：每轮间隔 20 秒、最多 3 轮，显示倒计时、每轮请求数与剩余套数；可随时「停止」；
- 如果某轮触发 `CAPTCHA_AUTH` / `SESSION_TIMEOUT`，自动停止并提示先去浏览器完成验证。

### 4.6 错误分类与请求预算（B3）

**错误分类**：服务端把藏宝阁的失败响应归类成 `errorCode`，前端分别给出「接下来该做什么」：

| errorCode | 用户该做什么 |
|---|---|
| `ITEM_NOT_FOUND` | 商品已下架/不存在 → 回模块一重新选一个在售账号 |
| `CAPTCHA_AUTH` | 在伴随服务的浏览器窗口里完成滑块验证 |
| `SESSION_TIMEOUT` | 在浏览器窗口里重新登录藏宝阁 |
| `MOBILE_AUTH` | 在浏览器窗口里完成手机验证 |
| `COMPUTE_PENDING` | 站点还在计算，稍后重新分析或自动取分 |
| `NO_CACHE` | 先点「开始分析」，再自动取分 |
| `API_ERROR` / `ANALYZE_FAILED` | 其他接口异常，显示原始信息 |

**请求预算**：分析结果里新增 `meta`：

```json
"meta": { "requestCount": 18, "durationMs": 20500 }
```

页面顶部会显示「本次消耗 N 个请求 · X 秒」；自动取分累计的请求数会并进 `requestCount`。
缓存命中时显示的是**原分析**的请求数与耗时，方便判断这个账号的分析成本。

### 回归校验

```bash
# A1/A2/A3：速度核心、分布、账号概览（离线，用缓存详情）
node tools/cbg/verify_analysis.mjs --file "<缓存详情.json>" [--file ...]

# B1/B3：自动取分计数、风控停止、错误分类（离线，用假 pageGet，不需要网络）
node tools/cbg/verify_retry.mjs

# 速度表边界（原有）
node tools/cbg/verify_speed_table.mjs --file "<缓存详情.json>"
```

### 为什么必须服务端代理

藏宝阁这三个接口**没有 CORS 头**（实测 `access-control-allow-origin` 为空），
浏览器从 `github.io` 或 `127.0.0.1:5173` 直接 `fetch` 会被拦。

**而且必须走已登录的浏览器页面，不能用 Node 裸 fetch。** 这一条是交了学费换来的：

| 阶段 | 匿名 Node fetch 的结果 |
|---|---|
| 一开始（低频） | ✅ 三个接口全部可用，连 Referer 都不校验 |
| 批量请求后 | ❌ `SESSION_TIMEOUT`「请登录之后继续访问」 |
| 更密集后 | ❌ `MOBILE_AUTH`「需要验证手机」——**连列表查询都一起被拦** |

所以在 `server.mjs` 里，`analyzeAccount` 的 `pageGet` 是通过
`Runtime.evaluate` 在**已登录的页面上下文里**发 `fetch`（带 `credentials: 'include'`），
和站点自己的请求完全一致，这才是不被拦的方式。

### 一次把接口打死的真实事故

第一版 `computePlan` 是「每套方案轮询最多 12 次」。须佐 5 套 + 阿修罗 11 套 =
16 × 12 = **192 个请求**，结果：

1. `compute_yys_heroes_plan` 立刻变成 `CAPTCHA_AUTH`「进行安全验证」
2. 紧接着 `get_equip_detail` 也变成 `SESSION_TIMEOUT`
3. 最后 `POST /cgi/api/query`（列表）要求手机验证 —— **模块一也一起废了**
4. 连**浏览器页面里**发同样的请求也会被拒（说明是账号/IP 级风控，不是请求头问题）

恢复只能等冷却或人工在浏览器里过一次验证。所以现在的实现是：

- `computePlan` 最多 2 次请求
- 一旦遇到 `CAPTCHA_AUTH` / `MOBILE_AUTH` / `SESSION_TIMEOUT`，**立刻停止后续所有方案的请求**，
  并把 `blocked` 标志返回给前端如实展示
- 检测到账号是「冷计算」（第一套就要等）后，后续方案只发一次请求排队，
  由用户稍后点「重新分析」取结果 —— 避免一次分析拖到 60 秒以上

### 不是每个账号都算得出来 —— 而且**与御魂数量无关**

第一次请求 `compute_yys_heroes_plan` 只返回：

```json
{ "status": 1, "computing": true, "msg": "该式神御魂搭配方式正在计算中！", "data": [] }
```

再请求一次（或点「重新分析」）才会拿到 `suit_vals`。已算过的账号站点侧有缓存，几秒就出分。

**但相当一部分账号会永远停在「计算中」，拿不到分。**

#### 实测样本（24 个账号 / 45 个「式神×首套方案」）

| 指标 | 结果 |
|---|---|
| 出分率 | **17 / 45 = 38%** |
| 相关系数（御魂数 vs 出分） | **r = −0.13**（几乎无关） |
| 出分账号的御魂中位数 | 2412 |
| 未出分账号的御魂中位数 | 2481 |
| 价格中位数（出分 / 未出） | ¥1350 / ¥1599 |

按御魂数分箱也看不出趋势：

| 御魂区间 | 账号 | 可评方案 | 出分 | 出分率 |
|---|---|---|---|---|
| <600 | 1 | 2 | 0 | 0% |
| 600–1500 | 7 | 11 | 5 | 45% |
| 1500–2500 | 6 | 12 | 6 | 50% |
| 2500–3500 | 5 | 10 | 4 | 40% |
| ≥3500 | 5 | 10 | 2 | 20% |

#### 重试也没用

对 4 个「算不出」的账号隔几分钟重探，**仍然 0 出分**。
所以这不是「等一会儿就好」，而是这些账号在站点侧就是算不出来。

#### 一条被自己推翻的结论（留档）

第一版只抽查了 5 个账号，看到「2596 件 → 5/5、293 件 → 0/5」就得出
「**与御魂数量强相关**」并且写进了文档。扩到 24 个账号后：

- 御魂 960 的账号出分，御魂 5107 的不出分
- 相关系数从 +0.53（12 个账号）翻成 −0.13（24 个账号）

**这是典型的小样本过拟合。** 教训：这类「看似有规律」的观察，
样本量不到 20~30 个别当结论写进文档。

#### 那到底由什么决定？

目前**无法从账号属性预测**。观察到的现象更像站点侧缓存命中：
被真实用户打开过「御魂搭配」页的账号会算出来，其余一直排队。

不确定的地方就说不知道——总比编一个「御魂要多」的规律好。
界面上只如实说「N 套方案没算出来」，不臆测原因。

### 独立命令行工具

命令行版走 Node fetch。**低频可用**，但风控升级后会失败——
它适合偶尔查一两个账号，不要拿去做批量。

```bash
# 账号评分（须佐之男 / 阿修罗）
node tools/cbg/account_score.mjs --url "<含 eid 的地址>"

# 只出速度表
node tools/cbg/soul_speed_table.mjs --serverid 47 --eid <eid> --sub-only
```

## 六、从模块一直接跳过来

模块一的表格每行都有一个「**评分**」按钮，点它会跳到：

```
#/score?eid=<eid>&serverid=<serverid>
```

模块二读取这两个参数后**自动开始分析**，用户不用再粘一次地址。

前提是列表接口每行都返回 `eid`（实测 15/15 都有），而 `serverid` 就是
`server_id` 字段。这两者在 `tools/cbg/scraper-service/server.mjs` 的 `mapRow` 里
都会保留，所以模块一 → 模块二不需要用户做任何额外操作。

## 七、已知限制

| 限制 | 说明 |
|---|---|
| 必须给 eid | 商品页地址只有 ordersn，无法推导 eid。但**从模块一点「评分」跳过来时不用管**——列表接口已经带上了 eid |
| **风控会连带影响模块一** | 账号评分的请求打多了，`/cgi/api/query`（模块一的列表）也会一起要求验证。所以不要把评分当批量工具用 |
| 分析耗时 | 方案多的式神要逐个算分。已缓存的账号约 6~18 秒；**从没算过的账号**只能先触发计算，需要用户稍后点「重新分析」 |
| 评分是懒计算的 | 第一次请求只返回 `computing: true`，站点算完才会有结果。界面会显示「N 套方案还在计算中」而不是假装有数据 |
| **约 6 成账号算不出分** | 实测 24 个账号 / 45 个「式神×首套方案」，出分率仅 38%。与御魂数量**无关**（r = −0.13），重试也不会变好。原因无法从账号属性预测，站点侧行为 |
| 依赖本机服务 | 页面需要通过伴随服务代理；公网页面同样需要先点「允许」本地网络访问 |
| 评分口径由站点决定 | `damage` 是藏宝阁自己的算法，我们只是读取，无法解释每一项权重 |
| 只覆盖有方案的式神 | 站点只为 31 个常用式神提供搭配方案；没出现的式神无法评分 |
| 缓存可能滞后 | 分析结果默认缓存 10 分钟：价格、收藏数、懒计算刚出的分在这段时间内可能是旧的。页面会标明「结果来自 X 分钟前的缓存」，点「刷新」可强制重抓 |
| 头/尾数量只认官方 | 「头/尾」的官方计数规则没有公开，页面直接引用官方 highlights 的「N头M尾」，不做本地推断（头速度可以本地复算并校验） |
